Direct inspection of the DATABASE_URL target (read-only queries, no writes)
confirms the function genuinely does not exist, and that the target database's
schema does not match supabase/migrations/*.sql at all:

  - `SELECT ... FROM pg_proc WHERE proname = 'reserve_inbound_channel_event'`
    -> 0 rows in any schema.
  - `SELECT version, name FROM supabase_migrations.schema_migrations`
    stops at 20260805000002 "secure_existing_tables" — a migration that does
    NOT exist anywhere under supabase/migrations/ in this repo. The repo's
    Phase 1-8 migrations (20260805010001_phase1_integrity_preflight through
    20260809030001_phase8_products_catalog) are not recorded as applied.
  - `information_schema.tables` on that database lists: audit_log,
    contact_consents, contacts, conversations, knowledge_chunks,
    knowledge_sources, memory_embeddings, memory_items, message_embeddings,
    messages, offerings, opportunities, pipeline_stages, products,
    qualification_answers, qualification_fields, sales_pipelines,
    sandbox_identities, workspace_contacts, workspaces.
    channel_events, channel_threads, contact_channel_permissions,
    consent_events, agent_decisions, outbound_deliveries, outbox_events and
    delivery_reports — all required by ingestion.service.ts / decision.service.ts
    — are entirely absent.
  - `contacts` in that database is missing lifecycle_status, sales_stage,
    blocked_at, blocked_reason (added by 20260805010002/…004), so even
    Scenario 5's SQL block step would fail against this schema.
  - `sandbox_identities` DOES exist with the exact columns the Phase 2
    migration defines (provider, external_user_id, contact_id,

    schema, suggesting it was created out of band rather than via
    `supabase/migrations/20260808010001_phase2_sandbox_identities.sql`.

Conclusion: the `DATABASE_URL` this backend is running against is not the
database the repo's migrations were written for/applied to. This is a real
infrastructure/environment defect, not a bug in run-pilot.mjs and not a bug in
ingestion.service.ts (its query matches the migration's function signature
exactly: 6x text, bytea, jsonb). No migration was modified, no backend code
was changed, and no workaround was added to the runner to route around this —
per instructions, scenarios 1-6 were left FAILING and this is flagged for a
human decision on which database/migration state to point DATABASE_URL at.
